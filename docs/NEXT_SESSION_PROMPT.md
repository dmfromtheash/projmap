Кандидаты (проверять замером, не верить на слово): WebGL-рендер Cytoscape (`renderer: { webgl: true }` в 3.31+, сверить версию и ограничения), уровень детализации по зуму (при отдалении — простые прямоугольники без SVG и подписей, при приближении — карточки), отсечение по видимой области, кэш текстур, разбор графа и сборка модели в Worker, инкрементальная перерисовка вместо полной пересборки элементов, ускорение `buildElements`/свёртки связей, инкрементальный скан (только изменённые файлы, кэш компиляций Roslyn) — цель скана Map < 15 с, обновление после правки файла < 2 с.

## Этап 2. Прогон Map: пустые зависимости, тупики, проблемные места

Добавь в projmap недостающие анализы как функции инструмента (видимые в окне и в `projmap-cli report`), затем примени их к Map:
- **мёртвый код**: классы и функции без входящих ссылок (исключая точки входа, тесты, публичный API, XAML/AXAML-привязки, DI-регистрацию, рефлексию, сериализацию — научи сканер видеть привязки `.axaml` и DI, иначе будут ложные срабатывания);
- **пустые зависимости**: `ProjectReference`/пакеты, которыми код не пользуется; using/импорты без использования;
- **тупики**: модули, папки и файлы, от которых ничего не зависит и которые ни от чего не зависят (кроме намеренно отдельных инструментов);
- **циклы** между модулями, папками и классами; нарушения слоёв (например, Core → Presentation; сверить с `docs/04_TECH_ARCHITECTURE.md` в Map);
- **проблемные места**: самые сложные функции, «боги»-классы (большой fan-in/fan-out), файлы-горячие точки по истории git, файлы, которые всегда меняются вместе, хотя лежат в разных модулях;
- **план ↔ код**: задачи дорожной карты без связи с кодом, код по закрытым этапам, который не трогали.

Каждую находку перед тем, как показывать владельцу, проверь сам по коду (открыть, поискать, при необходимости собрать) и отметь: подтверждено / ложное срабатывание (→ чинить инструмент). Итог — страница-отчёт с разбивкой по категориям и приоритету, с путями `файл:строка`, плюс снимки схем projmap на проблемных местах.

## Правила работы (обязательно)

- **Отвечай владельцу только по-русски, простыми словами.** Любой запрос на проверку или решение — с путём в интерфейсе, что смотреть и зачем.
- **Codex — только с разрешения на каждую задачу**: перед каждым запуском спроси (какая задача, модель `gpt-6.1-sol` или `gpt-6-astra`, уровень `high`/`xhigh`, запись или только чтение) и жди «да». Результат Codex проверяй сам. Долгие запуски — через `.cmd` и `Start-Process` (не `run_in_background` с лимитом 10 минут), промпт через `- < файл`.
- **Визуал делает только Claude** (вид схем, карточки, цвета, раскладка, интерфейс). Codex — анализатор, производительность движка данных, тесты, харнессы, отчёты.
- Разделение для параллельной работы, например: Codex — инкрементальный скан, новые анализы в `ProjMap.Analysis`, perf-харнесс; Claude — рендер, LOD, интерфейс, проверка находок, отчёт. Каждый трогает только свои файлы; согласуйте контракт графа заранее.
- **Окна тестов и проверок — только на ноутбучном (не основном) дисплее, на весь экран.** Основной экран — внешний 2560×1440; если подключён только ноутбук — можно на нём. Проверять прямоугольник окна, а не предполагать.
- **Map не сканировать «на запись»**: projmap читает репозиторий только на чтение. Не делать полный проход по интерфейсу самого Map (`--ui-tour`), если задача этого не требует.
- **Убирать за собой** все тестовые выводы, временные репозитории, профили, окна (Проводник, VS Code), если их открыла проверка.
- Не запускать сборку в `C:\Projects\Map` (устаревший checkout).
- Коммиты — в ветки, с понятными сообщениями; push и слияние — только по слову владельца.
- Не делай вывод «готово», пока не прогнаны: `dotnet test`, e2e-прогон, perf-замер и (для этапа 3) сборка и тесты Map.
