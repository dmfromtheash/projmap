## Этап 2. Анализы и проверка Map

Каждый анализ должен работать в двух местах:
- в projmap как функция инструмента: новые категории в графе или отдельный раздел отчёта, видимый в окне (вкладка/режим «Проблемы»);
- в `projmap-cli report <root> -o <файл>` — Markdown + JSON.

Затем примени анализы к Map.

1. **Мёртвый код.** Классы и функции без входящих ссылок. Исключать:
   - точки входа (`Main`, `App`, `Program`);
   - тесты;
   - публичный API библиотек;
   - **XAML/AXAML-привязки** — научи сканер читать `.axaml`/`.xaml`: `x:Class`, `{Binding …}`, `Command=`, `x:DataType`, стили и ресурсы;
   - **DI-регистрацию** (`AddSingleton<…>`, `services.Add…`, фабрики);
   - рефлексию (`typeof`, `nameof`, атрибуты), сериализацию (`[JsonSerializable]`, `[DataContract]`), переопределения и реализации интерфейсов, обработчики событий.

   Без этого будут массовые ложные срабатывания.
2. **Пустые зависимости:**
   - `ProjectReference` и пакеты, которыми код не пользуется (нет ни одного ребра `reference/call/inherit` в целевой модуль);
   - `using` без использования.
3. **Тупики.** Модули, папки и файлы без входящих и исходящих связей, кроме намеренно отдельных: инструменты, эксперименты, документы.
4. **Циклы** между модулями, папками и классами (компоненты сильной связности). **Нарушения слоёв** — сверить с `docs/04_TECH_ARCHITECTURE.md` Map: например, Core → Presentation или Rendering → App. Правила слоёв задавать данными (файл правил), а не кодом.
5. **Проблемные места:**
   - самые сложные функции (`metrics.complexity` уже есть);
   - «боги»-классы: большой fan-in/fan-out, много членов и строк;
   - горячие файлы по git: churn × сложность;
   - файлы, которые всегда меняются вместе, хотя лежат в разных модулях (`cochange` уже есть).
6. **План ↔ код:**
   - задачи дорожной карты без связи с кодом;
   - код по закрытым этапам, который давно не трогали;
   - упоминания несуществующих файлов и классов в документах.

**Правило проверки.** Каждую находку перед показом владельцу проверь сам: открыть файл, поискать использования (grep + Roslyn), при необходимости собрать. Отметка — «подтверждено» или «ложное срабатывание → починено в инструменте (тест)».

**Итог этапа.** Страница-отчёт (Artifact) по категориям и приоритетам, с путями `файл:строка` и снимками схем projmap на проблемных местах. Плюс список изменений инструмента. Map при этом не меняется: projmap читает его только на чтение.

## Этап 3. Названия и контекст

С помощью projmap найди в Map названия файлов, папок, классов и пространств имён, которые:
- непонятны без контекста;
- вводят в заблуждение;
- не совпадают с тем, что внутри;
- нарушают правила проекта.

Источники: русские роли из словаря `web/glossary.js`, описания из документации, связи по графу.

Для каждого названия:
- текущее имя;
- что там на самом деле;
- предложенное имя;
- почему;
- сколько мест затронет переименование (по графу и по grep, включая `.axaml`, строки и документы).

Заодно:
- пополни словарь `web/glossary.js`;
- допиши в сканер описаний то, что инструмент не смог объяснить.

**Переименования в Map — только после одобрения владельцем списка.** Порядок:
- пакетами, по протоколу этапов Map (отдельная ветка, `git mv`);
- сборка и **все** тесты Map зелёные;
- запись в его журнал/`STATE.md`, как требует протокол;
- затем пересканировать Map в projmap и показать «было/стало».

## Правила работы (обязательно)

- **Владельцу отвечать только по-русски, простыми словами.** Любой запрос на проверку или решение — с путём в интерфейсе, что смотреть и зачем.
- **Codex — только с разрешения на каждую задачу.** Модель `gpt-6.1-sol` или `gpt-6-astra`, уровень `high`/`xhigh`. Перед запуском назвать задачу, модель, уровень, запись или только чтение — и ждать «да». Результат Codex проверять самому, со своими замерами.
  - Долгие запуски — через `.cmd` и `Start-Process`, промпт через `- < файл`, конец — по файлу-флагу.
  - Codex работает в отдельной копии: `git worktree add ..\projmap-<задача> -b feat/<задача>`.
  - Разумное разделение: Codex — анализаторы в `ProjMap.Analysis`, `report`, тесты; Claude — окно, вкладка «Проблемы», проверка находок, отчёт, этап 3.
- **Визуал делает только Claude:** вид схем, карточки, цвета, интерфейс.
- **Запуск самой программы projmap для проверок владельцем заранее разрешён — не спрашивать.** Окна тестов — только на ноутбучном (не основном) дисплее, на весь экран. Основной экран — внешний 2560×1440; если подключён только ноутбук, можно на нём. Харнессы проверяют прямоугольник окна сами и закрывают окно, если оно попало на основной экран.
- **Map только на чтение для projmap.** `projmap-cli scan` всегда с `-o` вне Map: без `-o` он пишет в `<Map>/.projmap`. Не делать полный проход по интерфейсу самого Map (`--ui-tour`), если задача не требует. Не собирать в `C:\Projects\Map` — это устаревший checkout.
- **Убирать за собой:** тестовые выводы, временные графы, профили, окна, рабочие копии Codex после слияния.
- **Коммиты — в ветки, с понятными сообщениями; push и слияние в main — только по слову владельца.**
- Не говорить «готово», пока не прогнаны: `dotnet test`, e2e, perf-замер (окно не должно стать медленнее — сравнить с таблицей этапа 1), для этапа 3 — сборка и тесты Map.

## Подводные камни (узнано на этапе 1)

- **PowerShell 5.1** `Get-Content`/`Set-Content` без `-Encoding` портит UTF-8 (кириллица → кракозябры). Для правки файлов — Edit/Write или `[IO.File]::ReadAllText/WriteAllText` с UTF-8 без BOM.
- **Дисплеи переключаются в процессе:** внешний монитор подключают и отключают. Харнесс тогда закрывает окно, и прогон нужно перезапустить — это нормально.
- **Разрешения:** Claude не может сам выдать себе разрешения в `.claude/settings.local.json` (система запрещает самоизменение). Если подтверждения мешают, владелец добавляет правила сам через `/permissions`.
- **Cytoscape:**
  - `coll.not(coll)` квадратичен;
  - смена класса у тысяч элементов дорогая;
  - `opacity` на узлах каскадирует стили;
  - первая отрисовка элемента дорогая;
  - WebGL-режим не подходит.

  Подробности — в `docs/PERF.md`.
