**2. Представление «Ярусы»**

**Сценарий владельца.** «Покажи, где интерфейс, где правила программы, где сохранение; почему эти части связаны; есть ли зависимость ядра от интерфейса».

Пользователь может:

- раскрыть ярус до функциональных частей, модулей или файлов;
- посмотреть основание классификации: конкретный путь, импорт, базовый класс, правило;
- отфильтровать неопределённые и смешанные случаи;
- изменить ярус для узла, файла или набора путей;
- открыть связь между ярусами и увидеть исходные зависимости;
- выбрать архитектурный профиль и проверить его правила.

Предлагаемые стабильные ID: `frontend`, `application`, `domain`, `data`, `backend`, `infrastructure`, `tests`, `docs`. Отдельное состояние `unclassified` означает отсутствие надёжной классификации.

**Это категории ответственности, а не восемь ступеней строгой лестницы.** Например, сервер содержит прикладную логику, но серверный обработчик запроса и бизнес-правило выполняют разные роли. Тесты и документация вообще не образуют последовательный runtime-конвейер.

Поэтому кроме яруса нужны два независимых признака:

- `execution`: `desktop | browser | server | cli | shared | unknown`;
- `role`: например, `view`, `viewModel`, `useCase`, `entity`, `repository`, `schema`, `renderer`, `compositionRoot`, `buildTool`.

Это позволяет обозначить серверный React-компонент как интерфейс с `execution: server`, а рендерер Map — как runtime-инфраструктуру, общую для экрана и экспорта.

**Автоматические правила**

Сначала определяются границы модулей и признаки фреймворка из манифестов. Затем классифицируются файлы и, где возможно, отдельные типы/члены. Присутствие пакета в модуле само по себе не назначает ярус всем его файлам.

| Стек / источник | Правило классификации | Что не следует делать |
|---|---|---|
| Avalonia / WPF | XAML/AXAML, `Window`, `UserControl`, `Views`, `Controls` → `frontend/view`. ViewModel с состоянием экрана и привязками → `frontend/viewModel`. Независимые сценарии выполнения → `application/useCase` | Не считать весь `Presentation` прикладным ядром и весь `App` интерфейсом: там бывает сборка зависимостей |
| ASP.NET | Контроллеры, endpoint declarations, middleware, hubs → `backend`. Сервисы сценариев → `application`. Razor/Blazor UI → `frontend`, с отдельным execution | Не классифицировать каждый `Service` как backend |
| React / Vue | JSX/TSX-компоненты, Vue SFC, UI hooks/composables → `frontend`; чистые правила и модели классифицируются отдельно | Не считать любой `.tsx` браузерным кодом; не считать любой hook только интерфейсом |
| Next | Route handlers/API routes → `backend`; компоненты страниц → `frontend`; server actions классифицируются на уровне функции; `"use client"` уточняет execution | Не назначать всему `app/` один ярус. `"use server"` не означает автоматически HTTP endpoint |
| Express / Nest | Router/controller/middleware/gateway → `backend`; use-case providers → `application`; entities/value objects → `domain`; repositories/ORM adapters → `data` | Nest `@Injectable` — слабый признак: он не определяет ответственность |
| discord.js | Регистрация команд, `interactionCreate`, `messageCreate`, gateway adapters → `backend`, role `botAdapter`; независимые правила команд → `application/domain`; Prisma/SQL → `data` | Не считать команды Discord frontend-кодом только потому, что они видны пользователю |
| FastAPI / Django | HTTP routes, Django views/viewsets → `backend`; templates → `frontend`; ORM models/migrations → `data`; независимые модели предметной области → `domain` | Не путать Django `views.py` с визуальными Views Avalonia |
| Python CLI | `argparse`, Click/Typer, `__main__` → role `cliEntry`; сценарий продукта → `application`; сборочный скрипт → `infrastructure` | Не отправлять всё из `tools/` в инструменты разработки |
| SQL / ORM | DDL, миграции, DbContext/DbSet, Prisma schema, repositories, serializers, file stores → `data` | Наличие SQL в экспорте не делает весь модуль слоем хранения |
| Тесты / документы / инструменты | Тестовые манифесты, атрибуты, `.test/.spec`, CI, build scripts, Markdown → соответствующие категории | Тест сохраняет дополнительную связь «проверяет функцию X», но не становится production-кодом этой функции |

Для Vue и PHP сначала потребуется хотя бы распознавание расширений и структуры: сейчас `.vue` и `.php` отсутствуют в таблице языков `StructureScanner`. Для TS/JS/Python текущий анализ импортов лексический; он не даёт точности C# Roslyn. Это должно отражаться в `capabilities`, а не маскироваться высокой уверенностью.

**Уверенность и разрешение конфликтов**

Предлагаю объяснимую шкалу, а не псевдовероятность:

1. Для каждого яруса собираются свидетельства по семействам: синтаксис, зависимости, путь/имя, документация.
2. Внутри одного семейства учитывается максимум: десять совпадений `Views` не становятся десятью независимыми доказательствами.
3. Начальные веса: синтаксический признак — до `0.85`, явно заданная роль из структурированной конфигурации — до `0.95`, путь/имя — до `0.50`, наличие framework-пакета — до `0.15`.
4. При наличии только слабых признаков итог ограничивается `0.69`.
5. Автоматическое назначение: лучший результат ≥ `0.75` и отрыв от второго ≥ `0.15`. Высокая уверенность — ≥ `0.90`.
6. Два сильных противоречащих признака дают `mixed` или `ambiguous`, а не произвольного победителя.
7. Ручное назначение хранится как `decision: override`; оно не выдаётся за статистическую уверенность.

У контейнера лучше показывать распределение файлов по ярусам. Название «смешанный модуль» полезнее, чем ложное утверждение, что все его потомки относятся к одному слою.

**Направления зависимостей**

Стрелка означает «исходная часть зависит от целевой». Проверка выполняется по явным правилам, а не по порядку ярусов.

Пример профиля с независимым domain:

- UI → application: разрешено.
- Application → domain: разрешено.
- Data adapter → domain/interface: разрешено.
- Domain → UI/backend/concrete storage: запрещено.
- Backend → application: разрешено.
- Tests → production: разрешено; production → tests: запрещено.
- Остальное: `unspecified`, пока профиль не уточнён.

Для Map нужны также правила между конкретными модулями: например, `Rendering → App` нельзя надёжно проверить одной общей матрицей ярусов.

Результат связи: `allowed | forbidden | unspecified | uncertain | exempt`. Исключение содержит основание и при необходимости срок. При сомнительной классификации концов показывается `uncertain`.

`cochange` и `mentions` не участвуют в проверке архитектурного направления. `dbRead/dbWrite` проверяются отдельными правилами доступа к данным. Связи `implement/inherit` сохраняют исходное направление зависимости; переход к реализации при исследовании вызова — отдельная операция.

**3. Представление «История»**

Здесь необходимы три разные операции.

| Запрос владельца | Точная семантика |
|---|---|
| «Что менялось в октябре?» | Изменения за интервал: добавлено, изменено, удалено, переименовано |
| «Покажи проект на конец октября» | Состав и зависимости одного конкретного git-снимка |
| «Что затронул R13?» | Объединение изменений подтверждённых коммитов этапа плюс отдельно обозначенные ссылки из документов |

Текущий граф, отфильтрованный по `LastChange`, **не является прошлым состоянием проекта**: он теряет удалённые файлы и сохраняет сегодняшние символы и зависимости.

**Данные и вычисление**

1. **Индекс истории.** Хранить commit SHA, родителей, author date, committer date, сообщение и изменения путей с типами `A/M/D/R/C`. Для churn — добавленные/удалённые строки, у бинарных файлов значения неизвестны.
2. **Область истории.** Обязательны выбранный ref, пределы сканирования, shallow/truncated и полнота данных. Отсутствие события вне окна не означает, что файл не существовал.
3. **Состав на commit.** Читать дерево и blobs из Git через абстракцию источника файлов. Исторический анализ не должен переключать рабочую копию или исполнять проект.
4. **Исторические символы и связи.** Для точного уровня type/member нужны разборы соответствующих исторических blobs. Без них доступен точный файловый состав и честная пометка «семантика этого снимка не построена».
5. **Сопоставление версий.** Файловые переименования связываются через git rename evidence; копирование не считается той же сущностью. Для символов — сигнатура, контейнер, нормализованный синтаксис; неоднозначность сохраняется.
6. **Изменения символа.** Два уровня: «изменялся файл с этим символом» и «изменился сам символ». Второе требует сравнения символа между снимками; нельзя распространить churn файла на все его методы.
7. **Незакоммиченные изменения.** Отдельный срез «Рабочая копия», не часть последнего коммита.

`firstSeen` допустимо называть датой появления только при достаточном покрытии истории и прослеженной идентичности. Иначе это `earliestObserved`, сопровождаемое границей покрытия. `lastChanged` имеет явно указанную основу: содержимое файла, содержимое символа или просто изменение файла-владельца.

**Дата, ветка и этап**

Для календарной шкалы предлагаю по умолчанию:

- выбранная ветка;
- последовательность first-parent для снимков интегрированного проекта;
- committer date для группировки изменений;
- календарные границы в выбранном часовом поясе, сохранённые также как UTC-интервалы `[from, to)`.

Авторские даты доступны отдельно. Даты в Git могут идти немонотонно, поэтому выбор по календарю всегда разрешается в конкретный SHA, который показывается пользователю. Playback идёт по порядку истории, а не сортирует коммиты только по часам.

Этапы получают ключи вида `map/2026-10/R13`. Одинаковые `R13` из другой дорожной карты не объединяются автоматически. Для этапа отдельно хранятся:

- плановые даты;
- наблюдаемые даты активности;
- свидетельства завершения;
- множество связанных коммитов;
- необязательный подтверждённый снимок «после этапа».

Статус `done` не определяет снимок автоматически. Если у этапа нет однозначного commit/tag-якоря, доступно «что затронул этап», а для «проект после этапа» предлагаются кандидаты. Владелец может закрепить SHA.

**Документы и журналы**

Расширить текущий `RoadmapScanner`, выделив структурированные свидетельства:

- ключ этапа из заголовка;
- SHA из таблицы прогресса;
- точный ключ из commit subject;
- пути/символы из документа;
- запись журнала с датой и упоминанием этапа;
- DEC с датой и связями `supersedes/supersededBy`.

Приоритет связи: ручной якорь → явный SHA → точный ключ в commit subject → явный путь/символ → лексическое предположение.

Журналы — исторические свидетельства, не источник текущего статуса по умолчанию. Для настоящего исторического среза читается версия roadmap на соответствующем commit. Сегодняшний статус можно включить отдельным наложением.

Чтение этих коммитов дало:

Это объединение двух явно указанных коммитов. Другие документы могут добавить свидетельства, но не должны незаметно увеличивать счётчик «изменено коммитами этапа».

**Воспроизведение и исправления**

Playback поддерживает шаги «commit / месяц / подтверждённый этап». Для каждого шага показываются добавления, удаления и изменения. Сохраняются выбранная функция, детализация и область просмотра. Кадр не объявляется готовым до получения данных; устаревшие запросы отменяются.

Владелец может привязать этап к SHA, исключить неверно сопоставленный коммит, уточнить дату события и подтвердить переименование. Исправления сохраняют исходное автоматическое предположение для объяснения.

**Деградация, объём, риски.** Без Git остаётся шкала документальных событий и планов; точный состав на прошлую дату недоступен. При неполной истории показывается её граница. Активность и этапы — **M**; точные снимки с историческими символами — **L**. Основные риски: стоимость истории, rename ambiguity, слияния/cherry-pick и ложная точность дат.

**4. Представление «Функции / идеи»**

**Сценарий владельца.** «Покажи всё, что относится к экспорту, независимо от папки; от какой кнопки начинается работа; какие данные, тесты и этапы относятся к этой функции».

Функция — самостоятельная сущность со стабильным ID, названием, источниками, участниками и статусом подтверждения. Она может пересекать несколько ярусов и модулей. Этап дорожной карты может развивать несколько функций; функция может существовать десятки этапов.

**Предлагаемый алгоритм**

1. **Получить опорные точки.** Заголовки feature-документов, задачи с явным результатом для пользователя, точные ссылки на код, подписи обработчиков, команды CLI/Discord, маршруты API.
2. **Нормализовать термины.** Разбить `ExportPosterAsync`, namespace и пути на токены; учитывать словарь соответствий вроде «экспорт/export». Общие слова `service`, `manager`, `data`, `common` имеют низкий вес.
3. **Образовать первичные группы.** Документ с точными ссылками даёт сильную опору. Совпадение имени без связей — только кандидат.
4. **Расширить группу по графу.** Использовать разреженный граф зависимостей: `call` сильнее общего `reference`; import связывает файлы, но не доказывает конкретный вызов.
5. **Добавить co-change.** Использовать реальный Jaccard и число совместных коммитов, а не `edge.strength`. Существующий cutoff больших коммитов сохраняется.
6. **Не дать общим узлам поглотить группы.** Ослаблять вклад высокостепенных узлов. Логгер, контейнер DI, общий renderer или `index.ts`, соединяющий много функций, получает роль `shared`.
7. **Остатки группировать отдельно.** Для неохваченного кода — детерминированное распространение меток/сообщества в разреженном графе с фиксированными параметрами. Такие группы называются кандидатами, а не доказанными пользовательскими функциями.

Начальная оценка членства может комбинировать максимум по независимым семействам: документация, имя, семантический срез, co-change. Только имя и co-change не должны давать «подтверждено». Пороговые значения и версия алгоритма фиксируются в rule pack и проверяются на примерах.

Для большого проекта не строить все пары файлов: кандидаты берутся из индекса терминов, существующих рёбер и общих опорных точек.

**Срез от кнопки**

- Старт — конкретный handler или метод команды.
- Прямой обход `call`; `reference` используется ограниченно, с отдельным обозначением.
- Для вызова интерфейса добавляются возможные реализации через обратный индекс `implement`, для virtual — подходящие overrides.
- По умолчанию: глубина до 4, ограничение числа узлов, остановка на внешней системе и общих инфраструктурных узлах.
- Пользователь может раскрыть остановленную ветку.
- Результат называется **статическим возможным путём**, а не записанной runtime-трассой.

У C# это опирается на существующий граф. Для TS/JS/Python пока доступен срез импортов; полноценный путь от UI callback до вызванной функции потребует дополнительного анализа.

Реальный пример уже присутствует в Map: кнопка **«Слои отдельными PNG…»** вызывает `_editor.ExportLayersAsync()`, который обращается к `LayerPngExporter.WriteAsync`. [EditorView.PlayerPackage.cs](/C:/Projects/Map/src/Map.App/Views/EditorView.PlayerPackage.cs:20), [EditorViewModel.PosterExport.cs](/C:/Projects/Map/src/Map.Presentation/ViewModels/EditorViewModel.PosterExport.cs:47).

Для таких обработчиков стоит добавить `ownerMemberId` и anchor по имени контрола/месту регистрации. Текущий `#h<n>` оставляется совместимым, но не используется как единственное долговременное основание пользовательского назначения.

**Редактирование групп**

Владелец может переименовать, объединить и разделить группы, добавить или исключить участника, закрепить опорные точки, отметить общий код. Ручная группа получает стабильный ID, не зависящий от названия.

После пересканирования:

- название и явные include/exclude сохраняются;
- новые участники предлагаются;
- исчезнувшие участники отображаются как устаревшие ссылки;
- существенное изменение состава требует пересмотра, а не молчаливого переназначения.

Один узел может принадлежать нескольким функциям. Общие счётчики всегда считают уникальные узлы/файлы; сумма размеров функций не обязана равняться размеру проекта.

**5. Уровни детализации и сочетание представлений**

Предлагаемая последовательность навигации:

`проект → ярус → функция или модуль → файл → тип → член → обработчик`

Это **маршрут раскрытия**, а не новое физическое дерево. Некоторые ступени пропускаются:

- Python-функция может находиться прямо в файле;
- модуль может пересекать несколько ярусов;
- обработчик уже является членом, а его шаг означает «показать обработчики и их связи»;
- таблицы и документы имеют собственную детализацию.

Состояние представления можно описать так:

```json
{
  "groupBy": ["tier", "feature"],
  "detail": "file",
  "scope": { "featureIds": ["feature:export"] },
  "time": {
    "mode": "stageActivity",
    "stageId": "stage:map/2026-10/R13"
  },
  "include": {
    "tests": false,
    "docs": false,
    "contextNeighbors": true
  }
}
```

Правила взаимодействия:

- фильтры разных осей соединяются через AND; несколько выбранных функций внутри одной оси — через OR;
- сначала определяется временной набор данных, затем область и фильтры, затем группировка и детализация;
- соседние узлы вне фильтра можно показать как контекст, с явной отметкой; они не увеличивают счётчик выбранного набора;
- выбор сохраняется по исходному ID; если узла нет в историческом снимке, это сообщается явно;
- переключение ярусов и функций не сбрасывает время;
- возврат сохраняет предыдущую область, фильтры и детализацию.

Для комбинации «ярус × функция» логическая ячейка содержит пересечение множеств. В основной схеме узел имеет одно основное размещение; дополнительные принадлежности доступны как ссылки. По отдельной команде можно показать повторные представления узла с общим `canonicalNodeId`. Их метрики не суммируются повторно.

При превышении лимита раскрывается выбранная область. Само приближение камеры не должно внезапно перестраивать семантический уровень посреди жеста.

**JSON:** отдельный `ViewState`, не часть фактов сканирования. Для созданных блоков: `projectionId`, `canonicalNodeId?`, `groupKey`, `memberSetRef`, `contextOnly`.  
**Без данных:** пропускаются недоступные уровни; фильтры объясняют ограничение.  
**Объём:** **M**. Риски — потеря контекста при переключениях, дублирование метрик, взрыв числа пересечений.

| `TimelineEvent` | `id`, `kind: stage/decision/journal`, `occurredAt?`, `datePrecision`, `stageIds[]`, `commitIds[]`, `source`, `confidence` |
| `SnapshotDescriptor` | `id`, `commitId`, `treeId`, `capabilities`, `analysisFingerprint`, `resourceKey`, `status` |
| `FeatureMembership` | `featureId`, `nodeId`, `role: entry/implementation/test/doc/shared`, `decision`, `score?`, `evidenceIds[]` |

Полная история не должна раздувать каждый обычный `graph.json`. В нём достаточно coverage, этапов, агрегатов по периодам и дескрипторов. Подробные изменения и исторические графы загружаются из ресурсов AppStore по запросу. Для автономного экспорта можно включать данные внутрь документа отдельной опцией.

**Что кэшировать**

- Нормализованные признаки файла — по content hash и версии extractor.
- Назначения ярусов — по признакам, правилам и overrides.
- Feature-membership — по опорным точкам, выбранным связям и версии алгоритма.
- Git-изменения — по commit SHA; coverage и набор достижимых коммитов — отдельно.
- Исторический граф — по tree/commit, опциям анализа и доступным metadata references.
- Проекции и агрегированные связи — по fingerprint графа, времени, фильтрам, группировке и детализации.
- Раскладку — отдельно от смысловых данных.

Изменение overrides не требует полного Roslyn-скана. Изменение дерева коммитов не должно заставлять заново разбирать неизменившиеся blobs. Все кэши ограничены по размеру и могут быть удалены без потери ручных назначений.

**Производительность и корректность агрегирования**

Сохранить действующие пределы:

- **1500 блоков**;
- **1600 отображаемых связей**;
- **120 подсвечиваемых связей**.

Это пределы отображения, а не анализа. Все нарушения считаются до отсечения; интерфейс сообщает, сколько элементов скрыто, и позволяет сузить область. Нарушение не должно пропасть из отчёта только из-за малого веса.

Требования из [PERF.md](/C:/Projects/projmap/docs/PERF.md): FPS ≥ 58, худший кадр < 50 мс, блокировка < 200 мс. Это цели для будущих проверок, не измеренный результат предложения.

Необходимо сохранить `swapIn`, отмену устаревшего ELK и сбор вложенных маршрутов. Для больших графов вычисление проекции и кластеров вынести из UI-потока; ELK Worker сам по себе не ускоряет подготовку данных.

При движении по времени использовать кэшированные проекции и устойчивые позиции в пределах ограниченного окна playback. Не отправлять полный граф в новую раскладку на каждом движении ползунка.

Для рёбер:

- C# текущей версии — агрегировать finest-level связи;
- legacy file/type-представления — выбрать одно основание;
- `dbRead/dbWrite` сейчас дублируются на file/type — использовать файловое основание;
- `projectRef`, вызовы и импорты сохранять разными мерами;
- число коммитов контейнера — объединение commit IDs, а не сумма commits его файлов;
- docs aliases и повторные feature-представления не увеличивают LOC;
- для partial types файл изменения определяется по реальному `Path`/declarations члена, а не только по canonical parent.

Интеграция и компактные кэши — **M**; история снимков и её загрузка — **L**. Основные риски: устаревшие async-ответы, несовместимость сериализаторов, двойной учёт и неконтролируемый рост памяти.

После подключения новых видов следует повторить существующие perf-сценарии и добавить три: «Ярусы × функции», «переключение месяцев» и «срез от обработчика». Критерий — соблюдение текущих ограничений отзывчивости и сохранение полного набора результатов анализа при ограниченном количестве нарисованных элементов.
